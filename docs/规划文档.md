# 多平台代理 CDK 销售系统规划文档

> 产品形态：单站点、账号余额或在线支付、游客在线支付、订单展示 CDK
>
> 数据库：SQLite 单机持久化
>
> 技术栈：Go + Gin + GORM、Vue 3 + Vite
>
> 当前状态：一期业务范围已收敛，在线支付服务商待确定

---

## 1. 项目目标

建设一个统一销售多个代理平台 CDK 的简单商城。管理员维护商品和自备 CDK 库存。注册用户登录后可以选择账户余额或在线支付；不愿登录的游客只能使用在线支付。购买完成后，买家在订单详情中查看本次分配的 CDK。

### 1.1 支付矩阵

这是一期支付规则的唯一基线：

| 买家类型 | 是否登录 | 支付方式 | 必填凭证 | 查单方式 |
|---|---:|---|---|---|
| 注册用户 | 是 | 账户余额或在线支付 | 系统账号 | 会员中心查看本人订单 |
| 游客 | 否 | 在线支付 | QQ 或手机号 + 本单查询密码 | 订单号 + 联系方式 + 查询密码 |

硬约束：

- 注册用户每笔订单可以选择余额支付或在线支付。
- 游客没有账户和余额，必须使用在线支付。
- 所有购买路径共用商品、SKU、卡密库存和订单详情。
- 单笔订单只能选择一种支付方式，不支持余额与在线支付混合支付。

### 1.2 最短业务闭环

注册用户购买：

```text
管理员导入 CDK
    -> 用户登录并选择一个 SKU 和数量
    -> 用户选择余额支付或在线支付
    -> 余额支付：原子扣款并立即发卡
    -> 在线支付：预留 CDK，回调成功后发卡
    -> 用户在会员订单中查看 CDK
```

游客购买：

```text
游客选择一个 SKU 和数量
    -> 填写 QQ 或手机号及本单查询密码
    -> 系统创建待支付订单并预留 CDK
    -> 游客完成在线支付
    -> 支付回调验签并完成发卡
    -> 游客凭三项信息查单并查看 CDK
```

### 1.3 已确认决策

| 决策项 | 一期结论 |
|---|---|
| 站点 | 只有一个站点，不做多店铺或多租户 |
| 账号 | 注册用户使用本系统账号，不接入代理平台账号 |
| 商品来源 | 管理员导入多个代理平台的自备 CDK |
| 订单 | 一次结算只购买一个 SKU，可选择数量，不做购物车 |
| 注册用户支付 | 每笔订单选择账户余额或在线支付 |
| 游客支付 | 在线支付，一期只接一家支付通道 |
| 游客凭证 | QQ 或手机号，以及每笔订单单独设置的查询密码 |
| 发货 | 购买完成后在订单详情直接展示 CDK |
| 余额来源 | 管理员后台人工增加或扣减，完整记录流水 |
| 提现 | 不做 |
| 退款 | 不做站内自动退款流程或退款状态机 |
| 售后 | 不做自助补发、换卡、争议和工单系统 |

### 1.4 支持的平台

首批支持以下平台。平台只作为商品分类和卡密来源标识，不接入其用户或支付系统：

| 平台 | 官网 | 卡密来源 |
|---|---|---|
| CliProxy | https://cliproxy.com/ | 管理员导入 |
| Kookeey | https://www.kookeey.com/ | 管理员导入 |
| B2Proxy | http://b2proxy.com/ | 管理员导入 |
| 711Proxy | https://711proxy.com/ | 管理员导入 |
| IPWEB | https://www.ipweb.cc/ | 管理员导入 |
| BunnyProxy | https://app.bunnyproxy.com/ | 管理员导入 |
| UdealProxy | http://www.udealproxy.com/ | 管理员导入 |

平台数据不能写死。管理员后续可以新增平台、商品和 SKU。

## 2. 用户与权限

### 2.1 游客

- 无需注册或登录即可浏览商品和创建订单。
- 必须填写 QQ 或手机号，以及本单查询密码。
- 只能使用在线支付，不能读取或使用任何用户余额。
- 通过“订单号 + 联系方式 + 查询密码”查询订单。
- 只能在支付成功且订单完成后查看 CDK。

### 2.2 注册用户

- 可以注册、登录、退出和修改登录密码。
- 可以查看账户余额、余额流水和本人订单。
- 每笔订单可以选择余额支付或在线支付，不需要填写游客联系方式或查询密码。
- 余额不足时可以改用在线支付，或由管理员线下确认后在后台增加余额。

### 2.3 管理员

- 管理注册用户并人工增加或扣减账户余额。
- 管理平台、商品、SKU、卡密库存和全部订单。
- 查看全部在线支付记录及支付回调结果。
- 查看异常订单并人工处理，但一期不建设自动退款或售后工作流。
- 所有余额、卡密和订单管理操作必须记录审计日志。

### 2.4 权限硬约束

- 游客查单必须同时校验订单号、联系方式和查询密码。
- 登录用户只能读取自己的余额、流水、订单和 CDK。
- 游客不能调用余额购买接口。
- 未支付的游客订单不得返回卡密明文。
- 已售卡密不能再次入库、作废或分配给其他订单。
- 只有管理员可以调整余额以及导入、查看和作废未售卡密。
- 支付回调接口只能通过支付服务商签名改变在线支付订单状态。

### 3.1 商城与会员中心

| 模块 | 功能 |

| 商品 | 商品列表、详情、SKU、价格和库存状态 |
| 账号 | 注册、登录、退出和修改密码 |
| 会员余额 | 当前余额和余额流水 |
| 会员购买 | 单 SKU、数量、余额或在线支付方式选择 |
| 会员订单 | 本人订单列表、订单详情和 CDK |
| 游客下单 | 单 SKU、数量、QQ 或手机号、本单查询密码 |
| 游客支付 | 创建在线支付、跳转或展示收款页面、轮询状态 |
| 游客查单 | 订单号、联系方式和查询密码查询 |

### 3.2 管理后台

| 模块 | 功能 |
|---|---|
| 用户 | 查询、创建、启用和禁用注册用户 |
| 余额 | 人工增加或扣减余额，填写原因并记录流水 |
| 平台 | 新增、编辑、启用和停用平台 |
| 商品与 SKU | 新增、编辑、定价和上下架 |

| 订单 | 查询余额订单、在线支付订单及发出的 CDK |
| 异常订单 | 查看在线支付成功但发卡失败等异常 |
| 支付记录 | 查询商户订单号、渠道流水号、金额和回调状态 |
| 审计日志 | 记录余额、卡密、商品、用户和订单管理操作 |

### 3.3 明确不做

- 用户余额在线充值、余额提现、转账、佣金、邀请返利和分账
- 游客余额支付和单笔订单混合支付
- 多店铺、多租户、子代理、独立域名和主题换肤
- 购物车、多商品合并结算、优惠券和礼品卡
- 自动退款、退货、自助补发、换卡和工单系统
- 上游平台代理账号同步和 API 自动取卡
- 邮件、短信或 Telegram 发卡通知
- 多支付通道智能路由
- 开放 API、多语言、博客和 SEO

## 4. 账户余额

### 4.1 余额规则

- 金额统一以人民币“分”的整数存储，禁止使用浮点数。
- 余额只属于注册用户，游客没有余额记录。
- 用户余额只能由管理员后台人工增加或扣减。
- 余额只能购买 CDK，不能转账、提现或兑换现金。
- 余额不能小于 0。
- 每次余额变化必须产生不可修改的余额流水。
- 管理员调整余额必须填写原因和请求幂等键。
- 管理员扣减余额时，余额不足则拒绝操作。

余额流水类型：

```text
admin_credit   管理员增加余额
admin_debit    管理员扣减余额
purchase       用户购买商品扣减余额
```

### 4.2 注册用户余额购买

客户端提交 SKU ID、数量和全局唯一请求幂等键。应用使用 SQLite 写事务完成：

```text
1. 开启 BEGIN IMMEDIATE 事务
2. 校验登录用户、商品、SKU、数量和价格
3. 读取并校验用户余额 >= 订单总金额
4. 选取指定数量的 available 卡密
5. 余额或库存不足时回滚，不创建订单、不扣余额
6. 创建 payment_method=balance 的订单和价格快照
7. 扣减用户余额并写 purchase 流水
8. 将卡密改为 sold 并绑定订单
9. 将订单直接写为 completed
10. 提交事务并返回订单号和 CDK
```

扣减余额、写流水、创建订单和分配卡密必须在同一事务中完成。相同幂等键重复提交时返回原订单，不得再次扣款或发卡。

## 5. 在线支付

### 5.1 状态定义

在线支付订单状态：

```text
pending_payment   待支付，已临时预留 CDK
completed         支付成功并已发卡
expired           支付超时，预留 CDK 已释放
cancelled         创建支付失败或管理员取消未支付订单
delivery_failed   已确认收款，但发卡事务异常，需要管理员处理
```

余额订单创建成功后直接为`completed`，不经过以上在线支付状态。

支付记录状态：

```text
created   已创建渠道支付单
success   渠道确认支付成功
failed    渠道明确返回失败
closed    超时或渠道关闭
```

卡密状态：

```text
available  可销售
reserved   已为在线支付订单预留
sold       已售出并绑定完成订单
void       未售但已作废
```

### 5.2 创建在线支付订单

注册用户和游客共用在线支付流程。客户端都需提交：

- SKU ID 和数量
- 全局唯一的请求幂等键

游客还必须提交：

- 联系方式类型`qq`或`phone`
- 联系方式内容
- 本单查询密码

登录用户的在线支付订单直接关联`user_id`，不要求游客联系方式和查询密码。

应用使用 SQLite 写事务完成：

```text
1. 开启 BEGIN IMMEDIATE 事务
2. 校验商品、SKU、数量和价格
3. 登录用户绑定 user_id；游客规范化联系方式并生成查询哈希
4. 选取指定数量的 available 卡密
5. 库存不足时回滚，不创建订单
6. 创建 payment_method=online 的 pending_payment 订单和价格快照
7. 将卡密改为 reserved，写入订单 ID 和过期时间
8. 提交事务
9. 调用支付服务商创建支付单
10. 返回订单号、支付地址或支付参数、过期时间
```

若支付服务商创建支付单失败，系统将订单改为`cancelled`并释放预留卡密。同一个幂等键重复提交时必须返回原订单，不得重复占用库存或创建支付单。

### 5.3 支付回调与发卡

支付成功只能以服务商的服务器回调为准，浏览器跳转结果不能改变订单状态。

```text
1. 校验支付服务商、签名、商户订单号、金额和币种
2. 根据渠道流水号和回调事件做幂等检查
3. 开启 BEGIN IMMEDIATE 事务
4. 读取订单、支付记录和预留卡密
5. 重复成功回调直接返回成功，不重复发卡
6. 将支付记录改为 success
7. 将 reserved 卡密改为 sold
8. 将订单改为 completed
9. 写订单状态事件并提交事务
10. 按服务商规范返回回调成功响应
```

支付回调、在线支付订单完成和卡密售出必须在同一事务中提交。

### 5.4 超时与迟到回调

- 支付超时时间默认 15 分钟，可配置。
- 应用内定时任务释放已过期在线支付订单的预留卡密，并将订单改为`expired`。
- 应用启动时补扫过期订单，避免重启后库存长期占用。
- 支付渠道订单有效期应与本地订单有效期一致。
- 对过期后的迟到成功回调，先尝试重新分配同 SKU 可用卡密。
- 重新分配成功则正常完成；库存仍不足则记为`delivery_failed`，禁止静默吞单。
- `delivery_failed`只提供管理员异常处理入口，不扩展为完整退款或售后系统。

### 5.5 不退款边界

一期不提供用户自助退款、自动退款接口和退款状态机。正常完成并展示 CDK 的订单视为已交付。

在线支付成功但系统最终无法发卡属于异常，不得标记完成。管理员必须能看到该异常，并在支付服务商后台人工处理或补充库存。该人工动作不属于一期自动退款功能。

## 6. 游客联系方式与查单

### 6.1 联系方式

- 游客订单必须选择`qq`或`phone`类型。
- QQ 只接受数字；手机号允许国际区号，入库前去除空格和连字符。
- 联系方式原文加密存储，供管理员必要时核对。
- 另存带独立密钥的 HMAC，用于精确查单匹配。
- 联系方式不得出现在 URL、应用日志或支付回调日志中。

### 6.2 每单查询密码

- 查询密码由游客为每笔订单单独设置，长度为 6 至 32 个字符。
- 查询密码使用 Argon2id 或 bcrypt 哈希存储，不保存或回显明文。
- 查询密码只用于当前订单，不能通过找回密码接口恢复或由管理员查看、重置。
- 查询密码与注册用户的登录密码是完全独立的字段和认证逻辑。

### 6.3 游客查单

游客提交：

```text
订单号 + 联系方式类型 + 联系方式 + 查询密码
```

校验成功后：

- 未支付订单只返回订单状态、金额和支付有效期。
- 完成订单返回商品快照和 CDK。
- 失败时统一返回“订单信息不匹配”，不暴露具体哪一项错误。
- 按 IP、订单号和联系方式限流；连续失败后要求验证码。
- 查单接口使用 POST，请求凭证不得放在 URL 查询参数中。

## 7. 商品与卡密规则

### 7.1 商品和价格

- 一期固定币种为 CNY。
- 下单时保存商品名、SKU 名、单价、数量和总金额快照。
- 商品以后改名、改价或下架，不得影响历史订单。
- 每笔订单只含一个 SKU；需要购买其他 SKU 时另建订单。
- 余额购买和游客在线支付使用同一个 SKU 销售价。

### 7.2 卡密导入

- 支持一行一卡及`卡号----密码`格式。
- 导入前必须选择平台、商品和 SKU。
- 导入结果返回成功数、重复数、格式错误数和对应行号。
- 卡密标准化后使用带独立密钥的 HMAC 去重。
- 卡密正文使用 AES-GCM 加密存储，密钥来自环境变量。
- 密文记录密钥版本，便于以后轮换密钥。
- 卡密明文不得写入日志、错误响应或审计日志。

## 8. 系统架构

```text
浏览器
  -> Nginx / 宝塔反向代理（TLS）
  -> 单应用容器
       |- Vue 3 商城、会员中心与管理后台
       |- Go HTTP API
       |- 在线支付回调处理
       `- 在线支付订单过期扫描任务
  -> /app/data/card.db（SQLite 持久化文件）
```

### 8.1 技术选型

| 层 | 选型 |
|---|---|
| 后端 | Go + Gin + GORM |
| 前端 | Vue 3 + Vite + Pinia + Vue Router |
| UI | Element Plus |
| 数据库 | SQLite 3 |
| API 文档 | OpenAPI 3.1 |
| 部署 | Docker Compose 单应用容器 |

一期不需要 PostgreSQL、Redis、独立 Worker、消息队列、对象存储或 API Gateway。

### 8.2 SQLite 运行约束

- 只允许一个应用实例写同一个数据库文件，不支持多副本部署。
- 数据库文件必须放在持久化目录`/app/data`，不能写入镜像层。
- 启动时设置`PRAGMA journal_mode=WAL`、`foreign_keys=ON`、`busy_timeout=5000`。
- 涉及余额、订单、库存和支付状态的写入使用短事务。
- 外部支付请求不能放在数据库事务内部。
- 余额购买、在线支付下单、支付回调和释放库存使用`BEGIN IMMEDIATE`避免并发写入竞争。
- 备份使用 SQLite Backup API 或安全在线备份命令，不能只复制主数据库文件而忽略 WAL。
- 当单机写并发或数据量超出 SQLite 能力时再迁移 PostgreSQL。

## 9. 数据模型

### 9.1 用户与余额

```text
users
  id, username, email, password_hash
  role(user|admin), status(active|disabled)
  balance_cents, version
  created_at, updated_at

balance_ledgers
  id, user_id
  type(admin_credit|admin_debit|purchase)
  direction(in|out), amount_cents, balance_after_cents
  ref_type, ref_id, reason, operator_id
  idempotency_key, created_at
```

游客不写入`users`或`balance_ledgers`。

### 9.2 平台、商品与卡密

```text
platforms
  id, code, name, website, status, sort

products
  id, platform_id, name, slug, description, cover_url
  status, sort, created_at, updated_at

skus
  id, product_id, name, attrs_json
  sale_price_cents, status
  created_at, updated_at

card_batches
  id, sku_id, filename, total_count
  success_count, duplicate_count, invalid_count
  imported_by, created_at

cards
  id, sku_id, batch_id
  secret_ciphertext, secret_hash, key_version
  status(available|reserved|sold|void)
  reserved_order_id, reserved_until
  sold_order_id, sold_at, created_at
```

### 9.3 订单与支付

```text
orders
  id, order_no, user_id(nullable)
  payment_method(balance|online)
  contact_type(nullable: qq|phone)
  contact_ciphertext(nullable), contact_hash(nullable)
  query_password_hash(nullable)
  status(pending_payment|completed|expired|cancelled|delivery_failed)
  currency, total_amount_cents
  idempotency_key, expires_at(nullable)
  created_at, paid_at, completed_at

order_items
  id, order_id, sku_id
  product_name_snapshot, sku_name_snapshot
  unit_price_cents, quantity, subtotal_cents

order_cards
  id, order_id, order_item_id, card_id

payments
  id, order_id, provider
  merchant_order_no, provider_trade_no
  currency, amount_cents, status(created|success|failed|closed)
  pay_url, callback_event_hash
  created_at, paid_at, callback_at

order_events
  id, order_id, from_status, to_status
  event_type, ref_id, detail_json, created_at
```

数据规则：

- 余额订单：`user_id`必填，`payment_method=balance`，游客凭证和`payments`记录为空，创建成功即`completed`。
- 注册用户在线订单：`user_id`必填，`payment_method=online`，游客凭证为空，并且必须有`payments`记录。
- 游客在线订单：`user_id`为空，`payment_method=online`，联系方式和查询密码字段必填，并且必须有`payments`记录。
- 支付回调原文默认不完整落库，只保存排障必需且已脱敏的字段及事件哈希。

### 9.4 审计

```text
audit_logs
  id, operator_id, action, target_type, target_id
  before_json, after_json, reason, ip, created_at
```

### 9.5 必要约束与索引

- `users.username`和`users.email`唯一，`users.balance_cents >= 0`。
- `platforms.code`和`products.slug`唯一。
- `cards.secret_hash`唯一，`order_cards.card_id`唯一。
- `orders.order_no`和`orders.idempotency_key`唯一。
- 使用检查约束保证余额订单、注册用户在线订单和游客在线订单的字段符合对应身份及支付方式。
- `balance_ledgers(user_id, idempotency_key)`唯一。
- `payments.merchant_order_no`唯一，非空渠道流水号唯一。
- `payments.order_id`唯一，一笔在线支付订单只对应一家通道的一笔支付单。
- 为`cards(sku_id, status, id)`建立发卡索引。
- 为`cards(status, reserved_until)`建立释放库存索引。
- 为`orders(contact_hash, order_no)`建立游客查单索引。
- 为`orders(user_id, created_at)`和`orders(status, expires_at)`建立查询索引。
- 使用检查约束保证数量和金额大于 0。

## 12. 安全要求

### 12.1 余额安全

- 余额扣减、余额流水、订单和卡密分配在同一 SQLite 事务中提交。
- 任何余额调整和购买请求都必须有幂等键。
- 提现和转账接口不存在，游客接口不得读取余额字段。
- 后台余额调整必须填写原因，并记录操作人及调整前后余额。

### 12.2 支付安全

- 一期只实现一家在线支付服务商，注册用户和游客共用该通道。
- 支付密钥只从环境变量读取，不写入前端、数据库或 Git。
- 回调验证签名、金额、币种、商户号、商户订单号和渠道流水号。
- 渠道流水号和回调事件唯一，重复回调不重复发卡。
- 支付成功以服务器回调为准，不信任同步跳转或前端轮询结果。
- 回调成功提交本地事务后才能向服务商确认接收成功。
- 支付服务商必须支持 HTTPS 回调、签名验证、订单查询和明确的订单过期机制。

在线支付服务商是当前唯一未确定的外部依赖。开发前必须确认服务商、接口文档、签名算法、测试环境、回调重试规则和生产商户参数。

### 12.3 数据安全

- 登录密码和游客查询密码分别哈希，不能共用字段或认证逻辑。
- JWT 或会话密钥从环境变量读取，并支持退出失效。
- 卡密和游客联系方式使用 AES-GCM 加密。
- 登录、注册、余额购买、游客下单、查单和管理操作按 IP 及目标限流。
- 查单失败统一响应，防止枚举订单、QQ 或手机号。
- 卡密、联系方式、查询密码、支付密钥和完整支付回调不得写入普通日志。
- 管理员查看卡密、调整余额和处理异常订单必须写审计日志。
- 数据库备份与加密密钥分开保存。

## 15. 验收标准

一期上线前必须通过以下场景：

1. 管理员可以创建平台、商品和 SKU，并导入有效 CDK。
2. 重复卡密不会重复入库，格式错误能定位到具体行。
3. 管理员增减注册用户余额后，余额和流水金额完全一致。
4. 登录用户余额和库存充足时，只扣一次余额并获得指定数量的唯一 CDK。
5. 登录用户余额或库存不足时，不创建订单、不扣余额、不改变卡密状态。
6. 游客不登录即可创建订单，但缺少联系方式或查询密码时必须失败。
7. 游客不能调用余额购买接口，注册用户可以为单笔订单选择余额或在线支付。
8. 注册用户或游客选择在线支付但库存不足时，不创建支付单，也不留下预留卡密。
9. 注册用户和游客的待支付订单都能预留指定数量的唯一 CDK。
10. 在线支付超时后订单变为`expired`，预留卡密恢复为`available`。
11. 签名、金额、币种或商户号不匹配的回调不能改变订单状态。
12. 有效支付回调只完成一次订单，重复回调不会重复发卡。
13. 余额订单、注册用户在线订单和游客在线订单并发购买最后一张卡时，只有一个订单成功获得该卡。
14. 游客只有同时提供正确订单号、联系方式和本单查询密码才能查看订单。
15. 未支付游客订单和错误查单凭证均不能读取 CDK。
16. 登录用户不能读取其他用户订单，游客订单不能被订单号直接枚举。
17. 查询密码、联系方式和卡密正文不以明文存入对应字段或日志。
18. 注册用户或游客的有效支付回调在 3 秒内进入`completed`并展示正确数量的 CDK。
19. 迟到回调有库存时重新分配，无库存时进入`delivery_failed`并显示在后台。
20. 商品改名或改价后，历史订单快照保持不变。
21. 应用重启后能补扫全部过期在线支付订单并释放库存。
22. SQLite 在线备份、恢复、余额一致性和 CDK 解密读取至少演练一次。
23. Docker 部署后支付服务商能够访问 HTTPS 回调地址。
